# Извлечение текста из приложенного файла

Документ описывает **технологию распознавания и извлечения текста** из файлов, которые учитель прикрепляет на экране создания листа. Это отдельный этап — до генерации заданий через ИИ.

Как извлечённый текст попадает в промпты — см. [`PROMPTS.md`](./PROMPTS.md). Общая архитектура сервиса — [`SERVICE.md`](./SERVICE.md).

---

## 1. Задача

Учитель прикрепляет опорный материал (конспект, учебник, скан). Системе нужна **строка текста** — её передают модели как `reference_file.content`. Сам файл в готовый лист и экспорт не попадает.

Поддерживаемые форматы: `.docx`, `.pdf`, `.jpg`, `.jpeg`, `.png` (до 10 МБ).

---

## 2. Три технологии извлечения

В зависимости от типа файла используется **один из трёх методов**. Классический OCR (Tesseract и т.п.) **не используется** — для сканов и картинок применяется vision-модель (multimodal LLM).

| Метод | Когда | Библиотека / сервис | Нужен API-ключ |
|-------|-------|---------------------|----------------|
| **Парсинг Office Open XML** | `.docx` | JSZip + разбор XML | Нет |
| **Текстовый слой PDF** | `.pdf` с встроенным текстом | pdf-parse | Нет* |
| **Vision OCR** | PDF-скан, `.jpg`/`.png`, PDF с малым текстом | pdf-to-img + OpenRouter vision LLM | Да |

\* Для PDF на сервере ключ проверяется заранее: если ключа нет, PDF не обрабатывается (503). DOCX работает без ключа.

### Схема выбора метода

```
                    Файл от учителя
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
       .docx            .pdf          .jpg/.png
          │               │               │
          ▼               ▼               │
    JSZip → XML     pdf-parse:            │
    document.xml    текстовый слой         │
          │               │               │
          │         ≥ 200 символов?       │
          │          /         \          │
          │        да          нет        │
          │         │            │        │
          │    вернуть    pdf-to-img      │
          │     текст    PNG страниц      │
          │                  │            │
          └──────────────────┴────────────┘
                          │
                          ▼
              Vision LLM (OpenRouter)
              промпт + image_url base64
                          │
                          ▼
              Markdown + LaTeX + [описания]
                          │
                          ▼
              обрезка до 12 000 символов
                          │
                          ▼
              JSON { text, truncated? }
```

## 3. DOCX — парсинг Office Open XML

**Суть:** файл `.docx` — это ZIP-архив с XML внутри. Текст уже «цифровой», нейросеть не нужна.

### Как устроен DOCX

1. **JSZip** распаковывает архив.
2. Читается `word/document.xml` — основное тело документа в формате Office Open XML (пространства имён `w:`).
3. Из `<w:body>` последовательно обходятся блоки:
   - **Параграфы** `<w:p>` — текст из `<w:t>`, переносы из `<w:br/>`, табуляция из `<w:tab/>`.
   - **Таблицы** `<w:tbl>` — строки `<w:tr>`, ячейки `<w:tc>`. Ячейки строки склеиваются через ` | `, строки таблицы — через перенос.

### Преобразование XML → plain text

Теги удаляются регулярными выражениями (`stripXml`):

- `<w:tab/>` → `\t`
- `<w:br/>`, `</w:p>` → `\n`
- HTML-сущности: `&lt;`, `&gt;`, `&amp;`, `&quot;`
- Лишние пустые строки схлопываются

Результат — UTF-8 строка с сохранением абзацев и таблиц в текстовом виде.

### Ограничения DOCX-парсера

| Извлекается | Не извлекается / теряется |
|-------------|---------------------------|
| Обычный текст, списки, таблицы | Сложная вёрстка, колонки |
| Формулы OMML как XML-остатки или упрощённый текст | Качественный LaTeX из Word-формул |
| Структура абзацев | Изображения (только если есть alt-текст в XML) |

Для конспектов с обычным текстом и простыми таблицами метод надёжен и быстрый.

### Fallback в браузере (без сервера)

Если сервер вернул **503** (нет `OPENAI_API_KEY`) и файл — `.docx`, браузер сам распаковывает docx через JSZip, но **без таблиц** — только упрощённый `stripXml` по всему `document.xml`. PDF и картинки в этом режиме не обрабатываются.

## 4. PDF — текстовый слой или vision OCR

PDF бывает двух типов: **цифровой** (текст выделяется в просмотрщике) и **скан** (страницы — растровые картинки).

### Шаг 1: текстовый слой (pdf-parse)

Библиотека **pdf-parse** читает встроенный текстовый слой PDF и возвращает одну строку.

**Порог:** если текста **≥ 200 символов** (`MIN_TEXT_CHARS`), он сразу возвращается — vision OCR **не вызывается**. Это быстрый путь для учебников и статей, сохранённых «как PDF», а не отсканированных.

Если текста мало или pdf-parse упал с ошибкой — переход к шагу 2.

### Шаг 2: рендер страниц (pdf-to-img)

Для сканов и «пустых» PDF:

1. **pdf-to-img** рендерит каждую страницу в **PNG** с `scale: 2` (удвоенное разрешение для читаемости мелкого шрифта).
2. Обрабатывается не больше **N страниц** (по умолчанию 3, максимум 10 — переменная `CONTEXT_PDF_MAX_PAGES`).
3. Каждая PNG-страница отправляется в **vision OCR** отдельным запросом.
4. Тексты страниц склеиваются через `\n\n---\n\n`.

---

## 5. Vision OCR — multimodal LLM

Для **изображений** (jpg, png) и **страниц PDF-скана** текст «читается» не классическим OCR, а **vision-моделью** через OpenRouter API.

### Принцип работы

1. Байты картинки кодируются в **base64 data URL**: `data:image/png;base64,...`
2. На OpenRouter уходит `POST /chat/completions` с одним user-сообщением из двух частей:
   - **text** — инструкция распознавания (промпт ниже);
   - **image_url** — закодированное изображение.
3. Модель возвращает распознанный текст в ответе (`choices[0].message.content`).
4. Ответ очищается от markdown-картинок (`stripMarkdownImages`).

Параметры запроса:

| Параметр | Значение |
|----------|----------|
| `temperature` | 0.1 (минимум «фантазии») |
| Таймаут | 300 000 мс (`CONTEXT_EXTRACT_TIMEOUT_MS`) |
| Модель | `CONTEXT_OCR_MODEL` → иначе `OPENAI_MODEL` → иначе `qwen/qwen3-vl-235b-a22b-instruct` |
| API | OpenRouter (`OPENAI_BASE_URL`, ключ `OPENAI_API_KEY`) |

Ключ хранится **только на сервере**. Браузер не обращается к OpenRouter напрямую.

### Промпт распознавания

Модели явно задают формат выхода:

```
Распознай текст на изображении максимально точно.
Верни только результат без комментариев.
Сохрани структуру документа (абзацы, списки, таблицы).
Используй Markdown.
Все формулы запиши в LaTeX ($...$ и $$...$$). Если в формулах встречаются
незнакомые операторы (например, arctg, пиши их в формулах через \operatorname{})

Картинки, фото, схемы, диаграммы, вставленные изображения и любые нетекстовые
фрагменты на скриншоте не воспроизводи как изображения: для каждого дай краткое
описание в квадратных скобках.
Например: [логотип компании], [блок-схема], [скрин интерфейса кнопки].
Не используй синтаксис Markdown-картинок (![...](...)) и не вставляй ссылки на файлы или URL.
Не используй маркеры вида [РИС:1] и подобные — только обычные квадратные скобки с описанием.

Никаких пояснений до или после результата, только распознанный текст и описания в скобках.
```

**Почему так:**

- **Markdown** — сохраняет списки и заголовки для последующей генерации.
- **LaTeX в `$...$`** — формулы из сканов учебников остаются пригодными для математических заданий.
- **`[описания]` вместо картинок** — модель генерации получает смысл иллюстраций без бинарников; описания не должны попадать в задания ученику (правила в `CONTEXT_USAGE_RULES`, см. PROMPTS.md).

### Постобработка OCR-ответа

`stripMarkdownImages` удаляет из ответа модели:

- синтаксис `![alt](url)` — на случай, если vision-модель нарушила инструкцию;
- HTML-теги `<img ...>`;
- лишние пустые строки.

## 6. Обрезка и итоговый формат

После любого метода текст проходит **`truncateContextText`**:

- максимум **12 000 символов** (`CONTEXT_FILE_TEXT_MAX`);
- если обрезан — в ответе `"truncated": true`.

### API

**Запрос:** `POST /api/extract-context`, `multipart/form-data`, поле `file`.

**Успех:**

```json
{
  "text": "...извлечённый текст...",
  "truncated": false
}
```

**Ошибки:**

| HTTP | code | Когда |
|------|------|-------|
| 400 | `BAD_REQUEST` | Нет файла / неподдерживаемый формат |
| 413 | `PAYLOAD_TOO_LARGE` | Файл > 10 МБ |
| 503 | `NO_API_KEY` | PDF или изображение без `OPENAI_API_KEY` |
| 502 | `EXTRACT_ERROR` | Ошибка парсинга или vision OCR |

### Куда сохраняется результат

Браузер записывает в черновик:

- `contextFileName` — имя файла;
- `contextFileText` — извлечённый текст;
- `contextFileNote` — если текст не получен.

Бинарник файла **нигде не хранится** — только строка в `localStorage`. Распознанный текст в UI учителю не показывается.

## 7. Переменные окружения

| Переменная | Назначение |
|------------|------------|
| `OPENAI_API_KEY` | Ключ OpenRouter (обязателен для PDF и картинок) |
| `OPENAI_BASE_URL` | URL API (по умолчанию `https://openrouter.ai/api/v1`) |
| `CONTEXT_OCR_MODEL` | Vision-модель для OCR (приоритет над `OPENAI_MODEL`) |
| `OPENAI_MODEL` | Запасная модель, если `CONTEXT_OCR_MODEL` не задан |
| `CONTEXT_PDF_MAX_PAGES` | Сколько страниц PDF распознавать vision (по умолчанию 3, макс. 10) |
| `CONTEXT_EXTRACT_TIMEOUT_MS` | Таймаут одного OCR-запроса (по умолчанию 300 000) |
| `APP_URL` | Referer для OpenRouter |

---

## 8. Сравнение методов

| | DOCX (XML) | PDF текстовый слой | Vision OCR |
|--|------------|-------------------|------------|
| Скорость | Мгновенно | Быстро | Медленно (секунды на страницу) |
| Стоимость | Бесплатно | Бесплатно | Платный вызов LLM |
| Формулы | Часто некачественно | Зависит от PDF | LaTeX через промпт |
| Таблицы | Да (` \| `) | Зависит от PDF | Markdown-таблицы |
| Сканы | — | Не работает | Основной метод |
| Зависимость от ключа | Нет | Нет (но PDF требует ключ на сервере) | Да |

---

## 9. Ограничения

- **DOCX с OMML-формулами** — парсер не конвертирует Word Math в LaTeX; для формул лучше PDF со сканом или цифровым текстом + vision.
- **Длинные PDF** — распознаются только первые N страниц (по умолчанию 3).
- **Качество vision OCR** — зависит от модели (`CONTEXT_OCR_MODEL`), разрешения рендера (`scale: 2`) и качества исходного скана.
- **12 000 символов** — длинные конспекты обрезаются; модель видит только начало.

## 10. Пример: первая страница PDF «Задачи олимпиады»

Файл: PDF на 11 страниц (задачи для 5–6, 7–8 и старших классов). Ниже — что происходит с **первой страницей** при прикреплении к листу.

### 10.1. Что на странице

На первой странице — текстовая задача без встроенных иллюстраций:

- заголовок **«5–6 классы»**;
- условие про Смешариков (Бараш, Крош, Совунья, Ежик, Пин, Лосяш) и проход через Мышиную пещеру;
- список ограничений по времени (Совунья — 3 мин, Пин — 1 мин, …);
- блок **«Решение»** с пошаговым подсчётом: 1 + 1 = 2, + 3 = 5, … → **18 минут**.

Картинок на этой странице нет. На других страницах того же файла (задача про молочный комбинат) есть **схемы графов** — к ним вернёмся в [§ 10.4](#104-картинки-что-с-ними-происходит).

### 10.2. Какой метод сработал

Система **не** рендерила первую страницу в PNG и **не** вызывала vision OCR.

Причина: `pdf-parse` извлекает **весь текстовый слой PDF сразу** (все 11 страниц). Его длина сильно больше порога **200 символов** — срабатывает быстрый путь «текстовый слой PDF» (см. [§ 4](#4-pdf--текстовый-слой-или-vision-ocr)).

```
PDF (11 стр.) → pdf-parse → текст ≥ 200 символов → вернуть текст
                              (vision OCR не вызывается)
```

### 10.3. Извлечение и преобразование

**Шаг 1 — сырой текстовый слой** (фрагмент первой страницы, как отдаёт `pdf-parse`):

```
5-6 классы
1. 	Бараш, Крош, Совунья, Ежик, Пин и Лосяш отправились в поход к Голубому озеру. Путь предстоял не
близкий и к вечеру друзья добрались до Чертовой скалы. Перед ними открылся вход в проходную
Мышиную пещеру. Проход был такой узкий, что проходить одновременно могли не больше двух
путешественников. Кроме того, без фонаря идти в темноте было опасно. Фонарь был только один.
Бараш был напуган и хотел идти непременно в первой паре. Какое наименьшее суммарное время
затратили друзья для преодоления пещеры, если
• 	Совунья пересекла пещеру за 3 минуты,
• 	Пин затратил 1 минуту,
• 	Бараш ни на шаг не отставал от Пина, он боялся остаться один в пещере,
• 	Крош затратил 2 минуты,
• 	Ежик вышел из пещеры через 3 минуты,
• 	Лосяша не могли дождаться 5 минут?
Решение:
18 минут.
1 минута
+1 минута = 2 минуты
+3 минуты = 5 минут
+1 минута = 6 минут
+5 минут = 11 минут
```

Что видно в «сыром» виде:

- переносы строк **посередине предложения** (особенность текстового слоя PDF);
- табуляция после номера «1.» и маркеров «•»;
- маркеры списка сохранены как символ `•`.

**Шаг 2 — `truncateContextText`:** пробелы по краям обрезаются (`trim`). Если весь документ ≤ 12 000 символов — текст не режется (`truncated: false`). В данном файле лимит не достигается.

**Шаг 3 — ответ API:**

```json
{
  "text": "5-6 классы\n1. \tБараш, Крош, Совунья...",
  "truncated": false
}
```

**Шаг 4 — черновик:** строка целиком (все 11 страниц) попадает в `contextFileText`. Первая страница — только начало этой строки; при генерации модель видит **весь** извлечённый текст, не постранично.

`stripMarkdownImages` на этом пути **не вызывается** — vision OCR не использовался.

### 10.4. Картинки: что с ними происходит

#### На первой странице

Картинок нет → нечего удалять и нечего описывать.

#### На других страницах того же PDF (графы задачи про молочный комбинат)

Здесь важный нюанс **именно этого файла**:

| | Что происходит |
|--|----------------|
| **Фактически** (текстовый слой) | Схемы графов **не попадают** в `contextFileText`. Остаётся только подпись «Создаем нагруженный граф…». Картинки не «убираются» — они **никогда не извлекались**. |
| **Если бы** PDF был сканом (vision OCR) | Каждая страница → PNG → vision-модель. По промпту схема стала бы текстом в скобках, а не картинкой. |

**Пример vision OCR** (гипотетически, страница со схемой графа — как ответила бы модель):

```
7-8 классы
2. Менеджер молочного комбината начинает работать в 8.00 утра...
Решение:
[граф из 12 вершин с подписанными рёбрами и весами в минутах]
Создаем нагруженный граф с цифровой нумерацией вершин.
```

Если модель нарушит инструкцию и вернёт markdown-картинку:

```
![схема маршрута](data:image/png;base64,...)
Создаем нагруженный граф...
```

**После `stripMarkdownImages`** (регулярки `![...](...)` и `<img ...>`):

```
Создаем нагруженный граф...
```

Строка `![...](...)` **удаляется целиком** — в контекст для ИИ не попадает ни URL, ни base64. Поэтому в промпте распознавания модели просят описывать иллюстрации **сразу** в `[квадратных скобках]`, а не через `![](...)`.

**Итог для приложенного PDF:**

- страница 1 → чистый текст через `pdf-parse`;
- страницы 4–9 с графами → в текущем сценарии **только подписи**, без схем;
- `stripMarkdownImages` — страховка **только для vision OCR**, не для текстового слоя.

## 11. Что дальше

Извлечённый текст один раз сохраняется в черновике. При генерации плана, листа или одного задания он передаётся в user JSON как `reference_file.content` — **файл повторно не загружается**.

Правила использования материала моделью — в system-промпте (`CONTEXT_USAGE_RULES`). Подробности: [`PROMPTS.md`](./PROMPTS.md).
